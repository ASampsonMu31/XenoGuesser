MULTIPLAYER INTEGRATION PLAN
============================
Branch: Multiplayer1
Goal:   two players (Employee 119-A, the host, and 119-B, the joiner) play the same
        world together over Steam: a host/join panel with a 5-letter room code, the
        host's world seed shared so both PCs generate the same planet locally, a
        two-spaceman loading screen, a synchronised start, both players on the pod's
        stairs side by side, each seeing the other walk about live, and the guess
        reveal and shop held until both players are done.
Source: the networking comes from a minimal working Steam P2P test app (Swing UI,
        not used here) at C:\Users\Alexs\coding_projects_local\steamworks_multiplayer_app
        (SteamP2PApp.java, steamworks4j-1.10.0.jar, steam_api64.dll, steam_appid.txt
        containing 480). The parts worth keeping are summarised in BACKEND REFERENCE
        below so a session does not need that folder open, but read the original if
        it is available.

HOW TO USE THIS FILE
- Read this first at the start of every multiplayer session; it already records where
  everything lives in the game, so do not re-explore the whole codebase.
- Work the phases in order. Tick [x] items as they land and add a line to the LOG at the
  bottom (date, what was done, anything surprising).
- If a decision changes, edit the DECISIONS section rather than adding a contradiction
  lower down. OPEN QUESTIONS are for the user: ask, then move the answer into DECISIONS.
- One phase (or part of one) per conversation, then start a fresh conversation.
- Singleplayer must keep working exactly as before after every phase (no Steam needed to
  play singleplayer; Steam is only started when Play Multiplayer is pressed).
- Match the code style around you: long descriptive comments in plain English, British
  spelling (colour, centre), small private helpers, no new frameworks.

DECISIONS (settled; change here if they change)
-------------------------------------------------------------------------------
M1  Transport: Steamworks via steamworks4j 1.10.0, the old ISteamNetworking P2P API and
    ISteamMatchmaking lobbies, exactly as the test app does it. App ID 480 (Spacewar,
    Valve's shared test app) until XenoGuesser has its own app ID.
M2  Steam is started lazily the first time Play Multiplayer is pressed, never at launch,
    so singleplayer runs with Steam closed. If SteamAPI.init() fails the panel says
    "Steam isn't running. Start Steam and try again." and stays usable.
M3  One dedicated "steam-net" thread owns every Steam call (init, callbacks, lobby calls,
    send/receive), like the test app's networking thread with its steamTasks queue. The
    UI thread and the GL thread never call Steam directly: they post Runnables to the
    queue, read immutable snapshots (volatile / AtomicReference), and receive events via
    SwingUtilities.invokeLater. SteamAPI.runCallbacks() runs every ~10 ms on that thread.
M4  Room codes are 5 letters from "ABCDEFGHJKLMNPQRSTUVWXYZ" (I and O left out so they
    can't be mistaken for 1 and 0): 24^5 = 7,962,624 codes. Keep the test app's
    collision handling (search for the code before creating, verify after publishing,
    retry up to 20 times). Typed codes are upper-cased and filtered to that alphabet.
M5  Same world, same rounds: the host picks the seed (System.currentTimeMillis(), or
    -Dxenoguesser.seed if given) and sends it with its GameMode and MapKind; the joiner
    adopts all three (overriding its own menu choices). Each PC generates the world
    itself from the seed. Every random choice that must match between the two PCs
    (landing site, time of day, season, weather) is drawn from a Random seeded from the
    world seed AND the round number, made fresh for each round, e.g.
      new Random(worldSeed * 0x9E3779B97F4A7C15L + round * 0xBF58476D1CE4E5B9L)
    rather than from one long-lived spawnRandom, so the two PCs cannot drift apart if
    one of them happens to draw an extra number. Things that may differ per PC (people,
    cars, animals wandering, shop prices) stay local.
M6  Roles and colours: the host is Player 119-A, BLUE; the joiner is Player 119-B, RED.
    "Blue"/"red" replace the dark grey PART_TRIM parts (boots, gloves, back pack,
    helmet collar) only; the white suit, orange band and visor stay as they are.
    Starting colours (tune by eye):
      first-person trimColour (PlayerBody.render, today grey 0.5/0.51/0.54):
        blue 0.18, 0.36, 0.85    red 0.82, 0.16, 0.14
      turntable / world-drawn opponent (today 0.2/0.21/0.23, darker because lit):
        blue 0.08, 0.18, 0.55    red 0.55, 0.07, 0.06
    Singleplayer keeps the grey.
    REVISED (user, 2026-10-17): only the helmet collar ("neck thing"), the back pack and the
    front (chest) pack take the player's colour; the boots and gloves stay grey as in
    singleplayer. Done by giving the packs and collar their own mesh part,
    OrganismMesh.PART_SUIT_COLOUR (the shader's suitColour; grey in singleplayer). Applies to the turntable sheets (Phase 3b redoes
    spaceman_turntable_blue/_red.png) and later to the first-person body and the partner
    drawn in the world (Phase 5).
M7  Messages: one byte of type, then big-endian fields (java.nio.ByteBuffer, as the test
    app). Control messages are Reliable on channel 0; pose updates are Unreliable on
    channel 1 (a lost one is simply extrapolated over, per the brief). Every packet is
    checked: right sender (remoteSteamID), right length for its type; anything else is
    ignored with a log line.
M8  Pose updates go 5 times a second (every 200 ms), as in the test app.
M9  Extrapolation (dead reckoning) on the receiver, never interpolation-with-delay: the
    opponent is drawn where they are predicted to be NOW, from their last two updates.
    See Phase 5 for the exact rules.
M10 Development without two Steam accounts: all networking goes through a small
    Transport interface with two implementations, SteamTransport (real) and
    LocalTransport (a localhost TCP/UDP socket, for two game windows on one PC),
    chosen by -Dxenoguesser.mpfake=host or -Dxenoguesser.mpfake=join. Steam will not
    run two accounts on one PC, so without this every test needs two machines.
M11 In multiplayer the stairs are wider and both players start on them side by side:
    119-A on the left, 119-B on the right, as seen facing down the stairs, both facing
    down the stairs. Singleplayer's pod is unchanged.

M12 The multiplayer message is addressed correctly to each player, text AND audio. Two
    recordings with their own word timings: xenocorp_multiplayer_a.{wav,txt} for the host
    ("Good morning, Employee 119-A ... you have been paired with Employee 119-B") and
    xenocorp_multiplayer_b.{wav,txt} for the joiner (119-B, paired with 119-A). The
    ticker's word timings must match the new audio (Phase 3).
M13 Multiplayer scoring replaces quarter targets. There are NO productivity thresholds
    and no losing at a quarter end in multiplayer. At the end of each quarter, the player
    with the higher productivity that quarter wins it and gains quarter points equal to
    the quarter's number: Q1 = 1, Q2 = 2, Q3 = 3, Q4 = 4 (10 in all). A player who wins
    all of Q1, Q2 and Q3 (6 points against 0, more than the 4 left) wins at once: the
    game ends after Q3 ("irrecoverable lead"). Otherwise, after Q4 the player with more
    quarter points wins. Both PCs work this out from both players' productivity (sent
    with each GUESS, see PROTOCOL), so they always agree. Ties: see M17.
M14 The reveal shows both guesses, in this order: turn the globe to your own guess, then
    to the other player's guess, then to the true location, then draw the lines from
    each guess to it (your line and pin in your colour, theirs in theirs, M6).
M15 The players collide with each other (Phase 5).
M16 Lock-step stages: both players are always on the same stage of the game. Every
    transition between stages waits for both (Begin on the loading screen waits until
    both have pressed it; the round starts together; quarter verdicts and the game's
    end are shown together). The only exception is between a guess's reveal and the
    next round: one player may enter (and leave) the results and the shop before the
    other, but the next round starts for both together (Phase 7).

M17 Ties. Equal productivity in a quarter: nobody gets that quarter's points. Equal
    quarter points after Q4 (e.g. 5-5, or 0-0... any equal total): the game goes on to
    FINAL DECIDER rounds, one round at a time, played like any other round (same
    lock-step, reveal, shop). After each decider the player with the higher score in
    that round wins the game; if that round's scores are equal, another decider is
    played, until one is higher. Deciders use the per-round Random like any round
    (round numbers just carry on past the last normal round).

M18 Writing systems are NOT reproducible across PCs (see DETERMINISM AUDIT), so the host
    generates them and sends the files to the joiner:
    - Size: 4-7 alphabets of 10-40 letters, each a 64x64 PNG of a few hundred bytes to
      ~1.5 KB: roughly 50-250 KB in all. Steam's reliable P2P send takes up to 1 MB in
      one message, so it goes as ONE ALPHABETS message (a zip of ALPHABETS_DIR); under a
      second on any normal connection. (LocalTransport: the same bytes over the socket.)
    - Early start: the host chooses the seed the moment Host game is pressed and starts
      GlyphGenerator on a background thread straight away, while the room code is shown
      and the partner is still joining (it takes a few seconds; usually done before they
      connect). It sends ALPHABETS as soon as both the files exist and the joiner has
      connected.
    - The joiner doesn't wait for them to start loading: it begins generateWorld at once
      (sea level, rivers and climate don't use the alphabets) and only waits, if it must,
      just before the WORLD_LAYOUT stage, where InfrastructureManager reads
      NationScripts.available() and the sign atlases are made. It writes the files into
      its own RunFiles.ALPHABETS_DIR and skips GlyphGenerator entirely (so a PC whose
      PyTorch won't load can still join). Its terminal line for the first stage reads
      "Receiving writing systems from 119-A".
    - Check: the joiner's files are byte-identical to the host's (hash both, log).
M19 Everything that sets up a round is the same on both PCs, drawn from a Random made
    from (worldSeed, round) in multiplayer, never an unseeded one:
    - the landing site and pod (M5);
    - the sun: time of day, season (sun declination) and noon longitude
      (spawnPlayerAtRandomLocation / chooseTimeOfDay): already drawn from spawnRandom,
      so M5's per-round Random makes them match; the sun doesn't move during a round;
    - the weather: SphereWeather.newDay(dayRand, place) sets the day's cloud pattern
      (wind axis, offsets, wetness, streakiness) from that same Random, so it matches too.
      Two things still differ and must be fixed: the clouds drift with the listener's
      elapsed time since the game window opened (different on each PC), so in multiplayer
      pass seconds since the ROUND began (rounds start together, M16); and the cloud cover
      eases towards the rainfall where EACH player stands, so it can differ a little when
      they are far apart, which is fine (it's what's overhead);
    - the animals: which species live where is part of the world and already matches;
      where each round's individual creatures stand comes from OrganismManager.clear()'s
      roundSalt = new Random().nextLong(), which differs per PC. In multiplayer set it from
      (worldSeed, round) instead, so both players see the same animals in the same places at
      the start of a round (they then wander on their own on each PC; matching their
      movement isn't required).
    Traffic, people's walks and shop prices may stay different per PC.
M20 Same build, same Java: the lobby's "game" filter carries a build id (M1 note in
    BACKEND REFERENCE) and HELLO/START carry System.getProperty("java.version"); a
    mismatch shows "Your partner has a different version of XenoGuesser" (build) or a
    warning (Java). The packaged exe bundles its own Java 21 runtime, so exe-to-exe
    always matches; running from Maven uses whatever JDK is installed.
M21 Locale-proof text: every toLowerCase()/toUpperCase() that affects generation uses
    Locale.ROOT (PlanetName.acceptable and dictionary(), OrganismManager species names).
    This is about the PC's Windows region/language setting, not the game's language:
    Java's toLowerCase() with no argument follows the operating system's setting, and on
    a Turkish or Azerbaijani Windows it turns "I" into a dotless "ı". The game is English
    only, but a player in Turkey running it would then check names against the dictionary
    differently and could get a different planet or species name from the same seed. A
    one-line fix in each place.

M22 The settings menu (Esc) never pauses multiplayer. While one player has it open, the
    world carries on as normal on their PC (time, sun, weather, animals, traffic, round
    and network all keep going; POSE keeps being sent), and only that player's own input
    is locked (no walking, turning or map use). The other player notices no difference:
    the paused player's spaceman just stands still. If singleplayer's settings menu
    freezes anything in the world today, skip that freeze when Multiplayer is active.
M23 A disconnect mid-game (LEAVE received, lobby member left/disconnected, P2P failure,
    or 10 s of silence) ends the game, and the player who stayed WINS. The game-end
    panel (Phase 7b's final panel) says so, with the reason, e.g. "You win: Employee
    119-B disconnected", then "Main menu". Before the game has started (panel, loading
    screen) a disconnect just returns to the menu with a message, with no winner.

DETERMINISM AUDIT (2026-10-17): does the same seed make the same world on two PCs?
-------------------------------------------------------------------------------
Test: a headless tool (WorldFingerprint, kept out of the repo; easy to remake) built
seed 123 as XenoGuesser.generateWorld does, minus GL, and hashed each part. It was run
three times on one PC, imitating different PCs: 8 cores / 4 PyTorch threads (the game's
default here), 6 cores / 3 threads, 2 cores / 1 thread (JVM -XX:ActiveProcessorCount).
Result:
  IDENTICAL in all three: sea level and the map's join, terrain heights (20,000 sample
  points), climate, rivers (965 reaches, 359 lakes, every point), nations (14), settlements
  (340), roads (3,113 paths, every point), houses (10,214: place, size, seed), planet name.
  DIFFERENT: the writing systems. Same number of systems and letters each (fixed by the
  seed before the AI model runs), but 2 of 6 alphabets' glyph images differed in every run.
Why the world part holds: Java 17+ does all float/double arithmetic the same on every
  CPU (strict IEEE); every generator is seeded from worldSeed; parallel loops write to
  their own array slots or collect in order (toList); per-cell content (trees, rocks,
  houses, people) is seeded by cell id, so the order cells are built in (which depends on
  time budgets and thread count) doesn't change them; no settings, screen size or GPU
  feed into generation.
Why the glyphs don't: GlyphGenerator runs a PyTorch model (DJL, CPU). Its results vary in
  the last bits with the thread count (XenoGuesser.main sets it to half the cores) and can
  vary with the CPU's instruction set (AVX2 vs AVX-512 kernels). The letter-making then
  makes yes/no decisions on those numbers (stroke presence threshold, wellFormed, overlap
  > 0.62) and draws further random numbers depending on them, so a tiny difference
  changes whole letters. Fixing the thread count would not be enough across different
  CPUs, hence M18.
Not tested, by reasoning only:
  - Two different PCs (different CPUs): the Java-side world should match for the reason
    above; Java's Math.sin/cos/exp/pow/log use the same built-in routines on every x86-64
    CPU for a given JDK. Confirm with Phase 5's two-PC check.
  - Different JDK versions (Maven runs): those Math routines have changed between JDK
    releases, by up to one unit in the last place, which could tip a threshold. Hence M20.
    Exe builds all carry the same runtime (dist\XenoGuesser\runtime, Java 21).
  - If PyTorch fails to load on one PC, GlyphGenerator's failure is caught and the world
    goes on with fewer or no alphabets, which changes InfrastructureManager's culture
    count (NationScripts.available()). M18 removes this: the joiner never runs the model.
  - Per-round and live things not seeded from the world: spawnRandom (M5), creatures'
    roundSalt (M19), traffic and people's choices (Vehicles uses Math.random), weather
    as it evolves frame by frame, border lights (wall clock). Only the first two matter.
  - Locale: see M21.

BACKEND REFERENCE (from SteamP2PApp.java; keep this logic, drop the Swing)
-------------------------------------------------------------------------------
Libraries (Windows, 64-bit):
  - steam_api64.dll: Valve's library, loaded from disk by absolute path.
  - steamworks4j64.dll: inside steamworks4j-1.10.0.jar at "/steamworks4j64.dll";
    extracted to a temp file, then loaded.
  - Both through SteamAPI.loadLibraries(new SteamLibraryLoader() { loadLibrary(name) })
    where name is "steam_api" or "steamworks4j" and each is System.load(absolutePath).
  - steam_appid.txt (containing 480) must be in the process's working directory when
    not launched from Steam; SteamAPI.init() reads it. Then SteamAPI.init() (false =
    "Steam isn't running").

Objects made after init (all on the steam-net thread):
  steamUser   = new SteamUser(new SteamUserCallback() {});  mySteamID = steamUser.getSteamID();
  networking  = new SteamNetworking(new SteamNetworkingCallback() {
      onP2PSessionRequest(remoteID): accept only if we're in a lobby and remoteID is a
          member of it (loop matchmaking.getNumLobbyMembers / getLobbyMemberByIndex);
          remember remoteSteamID if not set; networking.acceptP2PSessionWithUser(remoteID).
      onP2PSessionConnectFail(remoteID, error): if it's our partner -> reset with a message.
  });
  matchmaking = new SteamMatchmaking(new SteamMatchmakingCallback() {
      onLobbyMatchList(count), onLobbyCreated(result, lobbyID),
      onLobbyEnter(lobbyID, perms, locked, response), onLobbyChatUpdate(lobby, user, by, change)
  });

Phases of the room state machine (enum Phase):
  IDLE -> (host) CHECKING_HOST_CODE -> CREATING_LOBBY -> VERIFYING_HOST_CODE -> HOSTING
       -> (partner enters) IN_ROOM
  IDLE -> (join)  LOOKING_UP_ROOM -> JOINING_ROOM -> (lobby entered) IN_ROOM
  A MatchAction enum (CHECK_HOST_CODE, VERIFY_HOST_CODE, LOOK_UP_ROOM) remembers why the
  last lobby list was requested, since onLobbyMatchList doesn't say.

Searching for a code (requestRoomSearch):
  matchmaking.addRequestLobbyListStringFilter("room_code", code, LobbyComparison.Equal);
  matchmaking.addRequestLobbyListFilterSlotsAvailable(1);
  matchmaking.addRequestLobbyListResultCountFilter(10);
  matchmaking.requestLobbyList();   // answer arrives in onLobbyMatchList(count)
  ADD for the game (not in the test app):
  - a second string filter "game" = "xenoguesser-<PROTOCOL_VERSION>" (and set that lobby
    data when hosting), so lobbies of other Spacewar (480) users and of other game
    versions are never matched;
  - matchmaking.addRequestLobbyListDistanceFilter(SteamMatchmaking.LobbyDistanceFilter.Worldwide)
    (present in steamworks4j 1.10.0, checked with javap); Steam's default only finds
    lobbies in nearby regions, so friends far apart wouldn't find each other.

Hosting:
  CHECK_HOST_CODE: count > 0 -> new code, search again; else
    matchmaking.createLobby(LobbyType.Public, 2).
  onLobbyCreated(OK): setLobbyData(lobby, "room_code", code), setLobbyMemberLimit(2),
    setLobbyJoinable(true); then VERIFY_HOST_CODE search: count > 1 -> change the
    lobby's code (setLobbyData) and verify again; else HOSTING, show the code.
  onLobbyChatUpdate(Entered, someone else): remoteSteamID = them, IN_ROOM,
    setLobbyJoinable(lobby, false).
Joining:
  LOOK_UP_ROOM: count == 0 -> "No open room found for code X"; count > 1 -> "matches
    more than one room"; else lobbyID = getLobbyByIndex(0); joinLobby(lobbyID).
  onLobbyEnter(Success): remoteSteamID = getLobbyOwner(lobby) (must not be me), IN_ROOM.
Leaving / failure (resetToStart): setLobbyJoinable(false), leaveLobby, closeP2PSessionWithUser,
  clear lobbyID/remoteSteamID/roomCode, Phase IDLE.
Partner gone: onLobbyChatUpdate with Left / Disconnected / Kicked / Banned for
  remoteSteamID -> "The other player disconnected."
Net loop (every 10 ms): run queued tasks; SteamAPI.runCallbacks(); send if due
  (networking.sendP2PPacket(remoteSteamID, directBuffer, P2PSend.Reliable, channel));
  while (networking.isP2PPacketAvailable(channel, size)) readP2PPacket(senderID, buffer,
  channel) and check sender == remoteSteamID. Buffers must be ByteBuffer.allocateDirect.

-------------------------------------------------------------------------------
PROTOCOL (PROTOCOL_VERSION = 1)
-------------------------------------------------------------------------------
type  name          dir    channel  fields after the type byte
 1    HELLO         B->A   0 rel    int version, string javaVersion (M20)
 2    START         A->B   0 rel    int version, long worldSeed, byte gameMode ordinal,
                                    byte mapKind ordinal, string javaVersion (M20)
 3    START_ACK     B->A   0 rel    (none)
 4    WORLD_READY   both   0 rel    (none)            this PC has finished loading
 5    BEGIN         both   0 rel    (none)            this player pressed Begin (M16)
 6    POSE          both   1 unrel  int seq, long sentAtMs (sender's clock),
                                    double x, y, z (eye, planet-centred SpherePosition),
                                    float fx, fy, fz (camera forward, world space),
                                    byte flags (1 = swimming, 2 = airborne)
 7    GUESS         both   0 rel    int round, double px, py, pz (pin direction), int score,
                                    int quarterProductivity (this quarter's total so far,
                                    including this guess: what M13 compares)
 8    SHOP_DONE     both   0 rel    int round         left the shop for this round
 9    ROUND_BUILT   both   0 rel    int round         next round's world is built here
10    LEAVE         both   0 rel    (none)            leaving on purpose (menu / quit)
11    STAGE_DONE   both   0 rel    int stageId       generic "I've finished this stage"
                                    for any other lock-step point (M16), e.g. the quarter
                                    panel's Continue; stage ids are listed in Multiplayer
12    ALPHABETS     A->B   0 rel    int length, bytes: a zip of ALPHABETS_DIR in one
                                    message (Steam reliable P2P allows up to 1 MB; M18)
Strings are a short (unsigned) byte count then UTF-8 bytes.
Handshake: B enters the lobby -> B sends HELLO (this also opens the P2P session; A
accepts in onP2PSessionRequest) -> A sends START -> B adopts seed/mode/map, sends
START_ACK and shows "Connected" -> A receives START_ACK and shows "Connected".
A mismatched version -> both show "Your partner has a different version of XenoGuesser."
Keep-alive: if nothing at all is received for 10 s while in a game, treat it as a
disconnect (POSE arrives 5 times a second, so silence means trouble).
