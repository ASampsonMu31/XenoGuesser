GEODESIC WORLD MIGRATION PLAN
=============================
Branch: TrueSphereAttempt (started by GitHub Copilot; Claude continues it)
Goal:   one latitude-independent 3D sphere world on the geodesic chunk grid.
        The Mercator chart survives ONLY for drawing the minimap/heatmaps and
        for converting a map click into a guess. Nothing in the live world uses it.
Why:    method 1 (Mercator chart + per-latitude stretch, branch Claude5) works but
        near 70 degrees the chart stretches about 3x, so streaming and conversions
        cost far too much. Areas around 70 degrees matter to gameplay.

HOW TO USE THIS FILE
- Read this first at the start of every session; do not re-explore the codebase.
- Work the phases in order. Tick [x] items as they land and add a line to the
  LOG at the bottom (date, what was done, anything surprising).
- If a decision changes, edit the DECISIONS section rather than adding a
  contradiction lower down.
- One phase (or part of one) per conversation, then start a fresh conversation:
  long conversations cost more usage per message.
- Effort: medium for porting; high only for Phase 1 design and for a bug that
  survives two medium attempts.

DECISIONS (settled; change here if they change)
-------------------------------------------------------------------------------
D1  Keep Copilot's foundation: SpherePosition (double, planet-centred
    Cartesian), GeodesicChunkGrid (icosahedral), geodesic terrain/water
    streaming, GeodesicCollision, sphere camera, camera-relative rendering
    (sphereCamera uniform), SphereSkyRenderer, SphereWeather.
D2  Do NOT keep Copilot's simplified stand-ins as the final systems:
    GeodesicRoadMesh and GeodesicSettlementMesh get replaced by the real
    InfrastructureManager ported to the sphere, then deleted.
D3  Port by LOCAL TANGENT FRAMES, not rewrites. A frame = origin SpherePosition +
    east/north/up unit vectors. Existing flat 2D code (house building, road
    meshing, paint, fences, steering, collision tests) runs in metres-like local
    (x, z) inside a frame and the results are lifted to the sphere with
    frame.toWorld(x, y, z). On a 15 km round planet a frame is accurate to
    a few cm over ~300 m, which is plenty for one house or road segment.
D4  Plan globally on the sphere, build locally. Road networks and settlements are
    planned with great-circle geometry on SpherePositions (or unit directions);
    each piece (road segment, house, sign, booth) gets its own frame at its
    own position. No piece spans more than one frame.
D5  Spatial lookups (segmentsNear, housesNear, borders, doorways, collision) are
    keyed by geodesic cell id (GeodesicChunkGrid at a fixed level), searching
    the cell and its neighbours. No (x, z) chunk grids remain.
D6  Every chart reference outside the map is a bug: Planet.stretch, trueArea,
    seenFrom, latitude-for-placement, the shaders' onSphere/bend/curve uniforms,
    Frustum's chart conversion. Delete these as each consumer is ported.
D7  Noise and region factors are sampled from 3D unit directions (no seams, no
    pole pinching). Keep the old 2D sampling only where the map needs it.
D8  One render path. When a system is ported, delete its flat-world branch in
    the shaders and GLEventListener in the same change. No dual flags left over
    at the end (sphereNativeTerrain etc. go).
D9  Units: true metres everywhere (PlayerBody.METRE = 10 game units/metre stays).

PHASE 3  INFRASTRUCTURE  (biggest phase; split across 2-3 conversations)
-------------------------------------------------------------------------------
3a Planning on the sphere
[ ] Settlements placed as SpherePositions (SettlementManager), urbanness
    looked up by direction.
[ ] Nations: getNationAt(direction) (nation map sampled in 3D or via the
    existing map lookup through a direction -> map conversion; map stays the
    authority for borders so the minimap matches).

    and smoothing by great-circle maths. Border straightening the same way.

    should barely change.

[ ] Batching: NationBatch meshes built per geodesic cell in camera-relative

[ ] Delete GeodesicRoadMesh, GeodesicSettlementMesh and their fields/futures

-------------------------------------------------------------------------------
EFFICIENCY RULES (to stretch the weekly allowance)
-------------------------------------------------------------------------------
- Patch with Python scripts written by the Write tool (no bash heredocs with
  quotes). Normalise CRLF. Avoid trailing-space anchors.
- Always mvn clean compile; the game must not be running while building.
- Batch test launches: one launch should check several things (equator + 70
  degrees via -Dxenoguesser.spawnat, screenshots via hudtest=shot). World load
  takes about 90 s, so every launch is expensive.
- Read only the parts of big files a step needs (grep first, then targeted reads).
- No debug code left in; temporary prints marked // TEMP and removed the same turn.
- Commit only when the user asks.
